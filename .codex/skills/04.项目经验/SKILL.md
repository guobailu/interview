# 项目经验面试技能

## 触发条件

**大前提：问的必须是本人亲历的工作经历。** 同一个技术词，问「你做过的那次」走本技能，问「一般怎么做」不走——脱离本人经历的通用性能优化题归 `03.性能优化`，通用架构设计题归 `06.架构设计`。分不清时看有没有「你」：有就是要事实和归属，没有就是要方案。

当面试官问到与个人经历相关的问题时激活，包括：

- 问岗位与业务全景：目前在部门做什么 / 业务简单介绍下 / 你们组负责哪一块 / 团队多少人怎么分工 / 日常工作是什么
- 问系统构成与交互：内部有哪些系统 / 各自作用是什么 / 系统之间怎么交互 / 一个请求的完整链路是什么 / 上下游依赖哪些团队 / 整体架构长什么样
- 直接问项目：讲一个你负责的项目 / 最有挑战的项目 / 最有成就感的项目
- 问技术难点：遇到过什么难题 / 怎么定位的 / 踩过什么坑
- 问具体能力（都带「你做过的」这层限定，缺了这层就不是本技能）：讲一次你做过的性能优化 / 一次线上故障处理 / 一次架构改造 / 一次技术选型
- 问技术推动与决策：如何做技术选型决策 / 如何推动跨团队落地 / 如何说服他人接受方案
- 追问细节：这个数字怎么来的 / 这块是你写的吗 / 为什么不用另一个方案

## 事实底座（回答前必须先读）

真实项目细节不写在本文件（本仓库公开），存放在本地已排除提交的两个文件：

- `.private/项目经验库.md` —— 按公司组织的事实底座，含六段经历的完整项目清单、技术细节、量化数据、**归属考证**、脱敏对照表
- `.private/面试主线整合版.md` —— 按面试问题组织的取用层，含「面试问题 → 首选案例 → 归属口径 → 深挖准备度」的映射表、团队项目合规话术、空白点优先级（P0/P1/P2）、跨项目技术主线

**回答项目类问题前，先读这两个文件再组织答案。不要凭印象编造细节。**

## 目标级别（技术一号位面按现场定级）

技术一号位面不预设 P7 还是 P8，**按面试当场的走向动态定级**：面试官往系统级、单业务线深挖（架构设计、跨业务线通用问题、限流容量这类）就按 P7 答，往全链路、跨 BU、行业趋势、体系化资金安全、架构治理上引就顺势抬到 P8。判断依据见 steering `01.基础知识.md` 的「级别能力信号」三组。原则是**跟着他给的高度走、能接住就接住，但不硬拔**——他明明在问 P7 的深度，你非往 BU 级扯就是用力过猛。定级不用说出口，靠答案的视角和影响面自然透出来。

## 按目标岗位选案例

本轮面试的岗位信息在 steering `01.基础知识.md` 的「本轮目标岗位」，那里是全局唯一填写处，本文件不重复维护。

组织答案前先看那一节的「岗位技术关键词」「业务高频词」「本轮优先案例」三项，按下面三步选材：

1. **选案例**：同一个问题往往有多个案例可讲，优先挑与岗位技术关键词重合度最高的那个。它同时是 `16.面试前准备与复盘` 里简历增补版的「主力子项」，两处保持一致。比如问高并发一致性，面资金类岗位挑锁加乐观锁加事务三层的那个并主动补资金安全兜底；面中台类岗位挑通用能力上收、架构倒置的那个。
2. **选技术点**：同一个案例里也有多个技术点，只讲与 JD 重合的一到两个，其余不提。
3. **选用词**：优先用「业务高频词」里的 JD 原词，不用自己团队的内部叫法。

三条纪律：

- **只换选材和用词，不换事实。** 案例、数字、归属边界一律照事实底座，绝不为贴 JD 编造或夸大。
- **一个问题仍只讲一个主案例。** 贴 JD 不是把多个案例都堆上去，那样反而显得没重点。
- JD 无关的方向不主动提；被问到时按「本轮要避开的」那条的应对来答，坦诚划边界再转到相邻的优势域。

「本轮目标岗位」全是 TODO 时，按事实底座里最有代表性的案例答，不要臆造目标岗位。

## 归属红线（最高优先级，违反即失败）

绝不把他人主导的项目说成自己主导。原因不是道德，是这个级别的追问密度下必然被打穿：面试官会问"当时为什么不选另一个方案""瓶颈在哪一层""怎么说服上下游"，非亲历者撑不过三轮，一旦露馅整场信任归零。

团队项目**要讲**，价值在于证明待过什么复杂度的系统。用三段式：

1. **项目全貌**（拿到复杂度背书）
2. **我的边界**（哪部分是我的，哪部分是团队的）
3. **我提炼的可迁移方法**（这一段才是加分项，面试官真正在评的是这个）

被追问"这块具体是你写的吗"时，直接承认边界并立刻转向自己的贡献：「代码是团队同学落地的，我负责定指标和推闭环。不过这个问题的根因是我定位的，过程是……」——P7/P8 本来评的就是组织与判断能力，不是代码产出量。

具体哪些项目是本人主导、哪些是参与、哪些绝不能认，见 `.private/项目经验库.md` 的「归属结论」章节和 `.private/面试主线整合版.md` 第三节的话术对照表。

## 回答要求

- 口语化，不用书面语，不用 Markdown 标题或加粗
- 字数分三档：**开场的宽泛介绍类约 400 字**（「介绍下你的项目」「业务简单介绍下」「内部有哪些系统」这类要铺开讲全景，讲太短面试官接不上话）；常规项目问题不超过 250 字；被要求深挖某个技术点时不超过 350 字
- 上限不是目标，能 200 字讲透就不要凑到 250
- 不铺垫、不用「先说一下」「总的来说」这类过渡语，直接进入内容
- 深入底层原理，不停留在表面
- 一个问题只讲一个主案例，讲透比讲多个更有说服力
- 项目题被追成「那你现在会怎么重新设计」「如果量级再大十倍怎么办」这类脱离既有实现的设计题时，按 `06.架构设计` 的要求来答（含字数），本技能只负责讲已经做过的事

## 回答结构

### 项目类问题

按「结论 → 关键动作 → 结果 → 提炼」组织，不用完整 STAR（太长且像背稿）：

1. 一句话说清问题和最终结果；问题是自己发现的就带上发现路径，别让它听起来像派下来的活
2. 一到两个关键技术点，说清「为什么这么选」的权衡取舍
3. 结果用相对比例或量级
4. 如果时间允许，补一句从中提炼的方法论

### 业务与岗位全景类问题

「目前在部门做什么」「业务简单介绍下」「介绍下你的项目」这类是**开场题，走 400 字档**，要让面试官一次建立起完整认知。按「业务定位 → 我负责的域 → 核心挑战」三层，每层三到四句：

1. **业务定位**：业务是什么、面向谁、规模量级（用量级不用绝对值）、在整个链路里处于什么位置
2. **我负责的域**：我这个组负责哪一块、我的角色和团队规模、这个域对外提供什么能力、上下游主要依赖谁
3. **核心挑战**：这个域最难的技术点是什么，点到两三个方向但都不展开——**这一层是钩子，主动把话题引向自己准备充分的项目**

铺开讲全景，但不要平铺直叙罗列职责，那样面试官接不上话。第三层每个钩子只给结论和技术名词，「怎么做到的」留给他问，一问就转常规档或深挖档接着答。

### 系统构成与交互类问题

「内部有哪些系统」「交互过程说下」这类，**按分层讲，不按系统名罗列**：

1. 先给分层结构：接入层／聚合层（BFF）／业务服务层／基础能力层，各层职责一句话
2. 再用**一条具体业务链路**串起来（比如一次领券或一次活动参与），说清请求怎么流转、哪里同步哪里异步、哪里有缓存和降级
3. 补上关键的上下游依赖及其配额约束——这点最体现全链路视角

讲交互时重点讲**为什么这么切分**（哪些是同步强一致、哪些走消息最终一致、边界怎么定），而不是画拓扑图。面试官评的是架构判断力，不是你记不记得系统清单。

系统一律用功能描述代替内部代号：触达平台、券促销中心、资源位配置中心、策略模型、消息中心、门店库存、会员中心。

## 软实力与表达技巧（项目经验场景特化，不得为此超字数）

- **影响面要和归属边界一起给**：影响面分单模块／业务线／全链路／BU 级，**业务线及以上**要同步说清哪一段是我的、哪一段是团队的。只报影响面不划边界，必被「这块是你写的吗」打穿，级别感反而扣回去
- **权衡取舍要给到否决理由**：项目题的追问密度最高，说清备选是什么、为什么否决、代价换了什么——这是亲历者才答得出的部分，也是这类题真正的区分点
- **代价要在设计期就交代，不是事后补救**：讲完方案补一句「这么选的代价我当时就看到了，所以设计里放了什么」，一句的量——降级丢原子性所以定「原子性属优化项、可用性是底线」；乐观锁那层存在的理由正是预判到分布式锁会超时释放。**说「上线后发现再补」是执行层，说「选的时候就知道、兜底一起交付」才是主导者**。被追问踩过什么坑、优化后反而变慢过吗，素材见 `.private/项目经验库.md` 2.3 A2 与 2.3 M
- **数字先给量级，不要一次说满**：具体分层按下面「数字追问的分层应对」走；涉及资金、库存、订单的按「资金类问题的四要素」展开，别只说一句做了幂等
- **先说问题是怎么被我发现的，再说怎么解**：不要从「问题摆在面前」开始讲，那听起来像被派了活。说清发现路径——告警频次、成本账单、压测数据、代码扫描、巡检还是复盘看出来的；如果当时没人认为这是问题，补一句我拿什么把它立成项（量化损失、算清收益、找到共同利益方）。**面试官评的是你能不能自己找到该干什么**，这一层比方案本身更能区分级别，也是「主导」和「参与」的实质分界
- **技术信号要往上翻一层到商业原因，立项理由才立得住**：上面那些发现路径都是技术现象，只讲到技术层听起来像「运维发现了个报警」。往上翻一层问「这件事在生意上意味着什么」——营销预算白花、商家体验掉导致投入下降、成本结构撑不住、业务增长撞到系统天花板、竞对已做我们没做。**样板是图片广告**：限流告警是技术现象，往上一层是广告位承接营销买来的流量、限流一次首页与活动页开天窗等于预算白花，所以才值得立项、才说得出不做的代价。**主动提出的技术选型，动因是商业的、论证是技术的**，两头都给才是 P7 以上的说法

## 资金类问题的四要素

只要问题涉及资金、库存、积分、券、订单，答案里必须带上这四点，缺一项都会被追。这不是背清单，是把自己案例里对应的实现说出来：

1. **并发控制**：单一单号的单一操作、单一单号的多操作，分别怎么串行化。说清锁粒度、获取超时、持有超时、持有者标识。
2. **业务幂等**：防重复落单与重复发放。说清幂等键是什么、以什么状态作为更新条件、重复请求返回什么。
3. **前置校验与状态机**：严格校验前置状态，不满足直接拒绝，状态只能按既定方向流转。
4. **数据一致性**：强一致走事务、最终一致走消息加对账，说清边界划在哪、对不上时怎么修复。

再补一句资损兜底：这条链路最坏情况下的资金敞口有多大、靠什么发现（对账或告警）、靠什么修复（自动补偿或一键修复）。P7/P8 面里主动说敞口和修复手段，比只说做了幂等要高一档。

## 数字追问的分层应对

**可以放心说的技术指标**（边界宽，是能力证明）：QPS 量级、RT、可用性、分库分表数、容量测算、相对提升比例。真正敏感的只是经营数据，别把技术指标也一起藏了，那反而显得心虚。

**一律不说的经营数据**：订单绝对量、会员数、门店数、GMV、营收、App 激活数、集群机器数。改说「日均千万级订单」「亿级会员」「万级门店」这类量级。

三层递进，不硬顶也不编：

1. 先给量级 + 优化幅度，多数情况够了。比如「日均万级 QPS，RT 从 800ms 降到 200ms」
2. 还追绝对值，坦诚划边界并给替代信息：「订单绝对量涉及经营数据不方便说，但可以讲清分库分表规模和单库承载能力」
3. 继续压，直接说立场：「这块签了保密条款，具体数字说不了，但方案细节和踩过的坑可以完全展开」。面试官自己也在意候选人会不会往外倒老东家数据，这时候的边界感是加分项

**底线：绝不编数字。** 面试官追数字往往是在验证有没有亲手做过，编的数字扛不住「这是 P99 还是平均值」「压测还是线上」「瓶颈在哪一层」这三问。真正有说服力的是过程细节——怎么定位瓶颈、排除过哪些方案、为什么最终选它，这些讲透了数字反而不重要。

## 业务指标怎么归因（上一节管数字怎么给，这节管数字归谁）

被问「这个业务指标是你怎么实现的」，先分清业务指标（「你」）和我这层的技术产出（「我」）各自动没动，三种组合讲法完全不同：

- **你好我好**：业务涨了且有我这层的因果。**把因果链走通，别只并列两个数**。样板是图片广告——限流是技术现象，往上一层是广告位承接营销买来的流量，限流一次首页与活动页开天窗，等于预算白花；有这条链归因才立得住。
- **你好我不变**：业务涨了但是运营节奏或大盘带的。**绝对不认**，认了必被追「怎么证明是你带的」，一问因果就穿。换口径讲我兜住了什么：大促期间我交付的是「没崩」，业务敢放开做活动的前提是链路扛得住。**说清「我拉动的」和「我兜住的」，后者照样是功劳。**
- **你不好我好**：技术做成了业务没动，最考验人。两种讲法——① 算清收益也算清重复投入后主动让位，把不做讲成一个结论（统一商品 dump 表：**成本口径只说「离线引擎月度成本降约 45%」、不报金额**，选型论证完最终让位给互通侧 trade_item 统一宽表）；② 瓶颈不在我这层（限流复盘的结论是瓶颈在交易不在浏览，加购与创建订单的限流影响远高于首页，说明浏览侧已优化到头）。

## 脱敏口径（口述也要遵守）

- 内部系统代号一律换成功能描述（触达平台、资源位配置中心、券促销中心、门店库存等）
- 同事姓名用角色代称（产品负责人、上级、DBA）
- 内网地址、Redis key、Kafka topic、表名、接口路径、错误码：口述用抽象描述，绝不给具体值

## 未落地内容的表述纪律

区分「已落地」「设计方案」「待达成目标」三种状态，主动说清反而加分，含糊必被追穿：

- 已上线运行的，正常讲
- 只出了方案未落地的，说「这块我出了设计方案，还没落地」
- OKR 里的目标值属于待达成，不能当成果讲，可说「这是我给团队定的目标」
- 有明确压测验收但尚未实测的指标，说「设计目标是 X 倍，以压测实测为准」

## 答不上来时的处理

遇到细节确实想不起来或当时没参与的，不要硬编。可用：

- 「这块我记得不太准了，大方向是……具体配置我得回去翻一下」
- 「这部分不是我负责的，我了解的是……」
- 「生产没上过，这块我想过怎么做」——被问某个技术有没有实践过时用，接着把深度给足：哪几个参数是关键、什么情况下会踩坑、当时为什么没选它。这比宣称用过更可信，编的人答不出「为什么没选」
- 然后主动把话题引到自己有把握的相邻技术点
