我会固定采用：意图优先→可执行性→规则粒度→最小覆盖。Skill 只覆盖与 AGENTS 冲突的条款，其余通用规则保留；若通用规则会让 Skill 无法完成，以任务完整性为先。
我的判断过程是这样的，拆成几层：
第一层，识别意图而不是死抠字面。你手动点名"设计(口喷)"或"架构设计"，这个动作本身传递了信息：你要的是这个 SKILL 的产出。如果我用100字去砍架构设计的方案，等于让你激活 SKILL 这个动作失去意义——你不会为了得到100字答案专门去激活一个要求300字的 SKILL。所以我优先满足"你为什么要激活它"。
第二层，看规则的可执行性。系统设计 SKILL 要求"类至少7个、关系超过8个、完整 PlantUML 加所有字段"，这跟100字物理上不可能同时满足。当两条规则不可兼得时，我选那条能让任务真正完成的。100字是风格约束，出完整类图是任务本身，任务优先于风格。
第三层，看规则的粒度。全局规则是给"没有更具体上下文"的场景兜底的默认值，SKILL 是针对特定场景写的专门规则。专门规则天然比默认值更贴近当前场景，所以覆盖它。这也是配置系统的通用逻辑，就像局部变量遮蔽全局变量。
第四层，冲突范围最小化。我不是拿 SKILL 整体推翻全局规则，只在真正冲突的那一项上（字数）让 SKILL 赢，其他没冲突的部分（口语化、电商Java专家角色、不用markdown标题）继续沿用全局。这样两套规则都最大程度被尊重。
喂给 Codex 的话，可以这么表述：遇到规则冲突时，先问"用户激活这个 SKILL 的目的是什么"，再判断"哪条规则不满足会导致任务失败"，选保任务的那条；且只在冲突项上覆盖，其余仍按通用规则。
