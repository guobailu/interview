# 设计(口喷) Q&A

## 1. 每个集群有一个线程池，多个任务，有的任务计算量很大，有的任务IO很大计算量很小，现在每个线程池拉取任务执行，可能出现有的线程池总是拉取到计算量很小的任务，有的总是拉取到计算量很大的任务，如何优化？
想先确认几个点：
1. 这些任务是同构的还是异构的？就是说任务类型是提前能区分的（比如有标签标记是CPU密集还是IO密集），还是只有执行了才知道？
2. 线程池之间是完全独立的还是可以互相窃取任务？
3. 现在的任务分配策略是什么？随机拉取、轮询、还是按队列FIFO？

## 2. 1.有标签标记是CPU密集还是IO密集 2.线程池之间是完全独立的 3.都可以。
说白了就是按任务类型分队列。既然有标签能区分CPU密集和IO密集，那就别混在一个队列里让线程池随机拉了。把任务按标签分成两个队列，CPU密集型一个、IO密集型一个，每个线程池交替从两个队列拉取，保证每个池子拉到的任务是混合的，负载就均衡了。或者更简单点，用加权轮询，每拉N个CPU密集的就必须拉一个IO密集的，比例根据实际执行时间调。再进一步，可以引入工作窃取，某个池子空闲了就去其他池子的队列里偷任务，ForkJoinPool就是这个思路。

## 3. 项目是GPS业务，每天有约 2w+台车传数据到我们这里储存。每天数据量大概在1亿左右。
问几个点先搞清楚场景：
1. 数据主要用来干什么，是实时轨迹展示、历史轨迹回放、还是要做统计分析（比如里程、区域热力）？
2. 上报频率大概多少秒一次，峰值并发大概多少台车同时上报？
3. 历史数据要保留多久，有没有冷热分层的需求？

## 4. 1.实时轨迹展示、历史轨迹回放、还是要做统计分析都有 2.上报10秒一次，峰值并发有1万 3.历史数据保留半年，有冷热分层的需求。
说白了这就是典型的时序数据场景，写多读少，分层存储是关键。
上报这块先用Kafka顶住，1万台车10秒一条，峰值也就1000QPS，Kafka轻松扛住，顺便做削峰和多消费者分发。
存储上做冷热分离：热数据放Redis存最新一个点的经纬度，实时轨迹展示直接查Redis，秒级响应。轨迹回放用HBase，rowkey设计成车辆ID+时间反转，同一辆车的轨迹连续存，按时间范围scan很快。半年数据量也就1亿多点几十倍，HBase随便扛。
统计分析这块不能直接查明细表，用Flink做实时统计，比如里程、区域热力这些提前算好存到MySQL或者ClickHouse，报表查预计算结果，别现算。
冷热分层就是热数据（比如最近7天）留HBase快速访问，超过一个月的数据转成Parquet丢HDFS，省成本，需要跑离线分析再拉出来算。
